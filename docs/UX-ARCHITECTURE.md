# Product experience and UX architecture

This document covers how the guest site and the admin console are put together:
- information architecture, design system and motion;
- merchandising and engagement analytics;
- bilingual admin and permissions;
- performance and quality gates.

It complements [`COMMERCE.md`](COMMERCE.md) (money), [`EXCEL.md`](EXCEL.md) (import/export) and [`UX-AUDIT.md`](UX-AUDIT.md) (the functional action audit).

## 1. Principles

- **Nothing fake.** Every control does something real. The action audit (§9) proves it on every build.
  - No invented reviews, ratings or availability, and no placeholder figures.
  - A photo that is missing becomes a branded gradient with an icon, never a stock image.
- **Content is data.** Every tile, offer, badge, section and label a guest sees is managed in the admin and published as a snapshot. There is no hard-coded marketing copy.
- **One engine per concern.** The redesign reuses the existing engines unchanged:
  - request/order pipeline;
  - commission engine and ledger;
  - guest identity;
  - publishing snapshots.
- **Arabic first-class.** Both apps work fully in Arabic (RTL) and English (LTR). Figures use Latin digits for finance readability.
- **Privacy by construction.** Engagement analytics keep only aggregate daily counters. See §6.

## 2. Guest site information architecture

`/h/:slug` has the following sections, all configurable in **Website & homepage**:

| Section | Source | Notes |
|---|---|---|
| Hero | `hero_slides` + hotel profile | Greeting with the guest's name and room, primary CTA (slide CTA or "Explore services"), secondary CTA "Order to your room". Compact on mobile (`min(70svh,640px)`). |
| Quick actions | `quick_actions` | One-tap room requests. |
| Experiences | `experiences` entity | Bento grid; the first tile is large. When none are configured, tiles are derived from the published content (dining, wellness, services…). |
| Offers | `offers` | Carousel: scroll-snap, autoplay that pauses on hover/focus/touch/off-screen, dots and prev/next. Shows price, struck original, saving %, validity and badges. |
| Popular now | `catalog.featured_items` | Featured, recommended or badged menu items that are available now. Deep-links to `outlet?item=`. |
| Dining, wellness, services, info | catalog | Cards with open state, hours, location, delivery to room, WhatsApp and badges. |

Deep links:
- `?room=` pre-fills the room from a room QR.
- `dining/:outlet?item=:id` opens the item sheet.
- Offers open their target: outlet, spa category, service or package.

Tracking never blocks navigation.

## 3. Design system

- **Tokens:** CSS variables generated by the brand engine (`shared/theme.ts`): primary, secondary, surfaces, radius and font pair. Contrast is AA-checked when the brand is saved.
- **Components:**
  - `src/components/ui.tsx`: Button, Field, Toggle, Segmented, Dialog/Sheet, Img, EmptyState, ErrorState, Skeleton.
  - `src/guest/components/sell.tsx`: OfferCard, OfferCarousel, MerchBadges, PriceBlock, ExperienceGrid, PopularItems.
  - `src/guest/components/cards.tsx`: OutletCard, ServiceTile, SectionHeader.
- **States:** every data view has loading (skeleton), empty (icon, title and next step) and error (message and retry) states.
- **Logical properties:** layout uses `ms-/me-/ps-/pe-/text-start/text-end`, so RTL mirrors without overrides.

## 4. Motion

`src/guest/components/motion.tsx` defines one easing curve and three durations. Motion follows three rules:
- It explains change: page transitions, reveal on scroll, sheet entry and a carousel slide.
- It never gates content: everything renders first, then animates.
- `<MotionConfig reducedMotion="user">` turns movement into instant changes for users who prefer reduced motion. The carousel also stops autoplay for them.

## 5. Merchandising

- **Badges** (`MERCH_BADGES`): popular, recommended, new, limited time, hotel exclusive, best seller.
  - Available on offers, outlets, menu items, room/hotel services, spa services and laundry packages.
  - Validated server-side and shown bilingually.
- **Placement:** homepage section order and visibility are configured in Website & homepage. The `experiences` and `popular_items` sections are added automatically when content exists but the section was never configured.
- **Offers:** original price, promotional price, validity window, terms and a target. Expired offers are excluded from the bundle.

## 6. Engagement analytics (privacy-safe)

`POST /public/hotels/:slug/events` accepts batches of events from the guest site:
- Events: `offer_impression`, `offer_click`, `experience_click`, `service_view`, `menu_item_view`, `request_started`, `request_completed`, `whatsapp_click`.
- The body schema is `shared/engagement.ts`: 1–25 events per batch, target codes limited to `[A-Za-z0-9_-]`, at most 64 characters.

Storage:
- Only `guest_event_counts(hotel_id, day, event, target_type, target_code, n)` is kept, and `day` is the hotel-local day.
- No guest, session, device, IP or user agent is stored.
- Previews are not counted.
- The endpoint is rate-limited (120 per 10 minutes per client).

Transport:
- The client (`src/guest/track.ts`) batches events and flushes with `fetch(..., { keepalive: true })`. `sendBeacon` cannot carry the CSRF header.
- Impressions count once per page view, when at least half the card is visible.

Reporting:
- The admin dashboard shows seen/opened/CTR, request completion and the most-engaged content.
- It is visible only to roles with the hotel or offers module.

## 7. Admin console

### Navigation

| Group | Items |
|---|---|
| Overview | Dashboard |
| Operations | Requests (live queue), Guest relations & reviews |
| Guests & orders | Guests, Orders |
| Finance | Finance, Reports |
| Guest experience | Website & homepage, Experience categories, Offers & packages, Quick actions, Publishing history |
| Services | Dining & menus, Room services, Guest services, Wellness & spa, Laundry, Hotel information |
| Hotel setup | Hotel profile & settings, Brand & theme, Departments & WhatsApp, Media library, QR codes, Data import & export |
| Administration | Users & permissions, Audit log |

The platform area (Super Admin / Platform Finance) has its own navigation: commercial dashboard, agreements & rules, all orders, settlements, commission ledger and reports.

The top bar holds:
- a role chip;
- a new-request bell (polls every 30 s and deep-links to `requests?open=:id`);
- the language switch;
- publish controls, showing draft state, preview and publish.

### Bilingual admin

- `src/admin/i18n/index.tsx`: English source strings are the keys (`tr('Delete {0}?', { 0: name })`).
  - `L()` localises `{en, ar}` label maps.
  - `pickLang()` picks `name_en`/`name_ar` content.
  - `fmtDate`/`fmtNumber` use `ar-SA` with Latin digits and the Gregorian calendar.
- `src/admin/i18n/ar.ts`: about 1,550 entries. It is a **separate chunk, loaded only when Arabic is chosen**. The admin tree waits for it, so there is no English flash.
- **Server messages:**
  - `scripts/extract-server-messages.ts` extracts every API error string into `serverMessages.ts`.
  - `trMessage()` translates exact and templated messages (`Code {0} is already used`) and keeps the values.
  - It is registered once through `setApiMessageTranslator`.
- **Guards** (`tests/api/admin-i18n.test.ts`) fail the build when:
  - a JSX text node or text attribute contains raw English;
  - a `tr()` key has no Arabic;
  - shared constants or server messages have no Arabic;
  - placeholders differ between languages;
  - the server catalogue is stale.

### Permissions

- The server is the boundary: `roleCan(role, module)` plus department scoping on every route.
- The UI mirrors it: navigation is filtered by `roleCan`, and a restricted screen shows "Access restricted".
- `e2e/06-admin-language-permissions.spec.ts` checks, for every hotel role:
  - the exact set of navigation entries;
  - that a denied screen is refused;
  - that the server returns 403 for the same data (users, menu items).
- The action audit (§9) also fails on any 403 reached through a visible control. A visible button must never lead to a forbidden call.

### Finance controls

- Settlement maker–checker: the approver must differ from the creator and the reviewer.
  - The server returns `409 four_eyes`.
  - The UI disables Approve with an explanation.
- Commission calculations, snapshots and rule precedence were not changed by this pass.

## 8. Accessibility and responsiveness

- **Names and roles:** every button, link and input has an accessible name. This is enforced by `expectAccessibleNames` in E2E.
- **Control state:** toggles expose `aria-labelledby`/`aria-describedby`; segmented and device buttons expose `aria-pressed`; the selected list row exposes `aria-current`.
- **Dialogs and sheets:** they trap focus, close on Escape and return focus. This is tested.
- **Guest layouts:** checked for horizontal overflow at 320, 360, 390, 430, 768 and 1280 px in both languages (`e2e/03-responsive.spec.ts`). The Arabic admin is checked in RTL.
- **Carousel:** can be operated by keyboard and screen reader (labelled prev/next/dots, `aria-roledescription="carousel"`).

## 9. Functional action audit

`e2e/90-action-audit.spec.ts` logs in as every role (and as a guest on a phone viewport) and does the following:
- Visits every screen the role can reach.
- Clicks every visible control inside the main area.
  - Similar controls are capped per name family.
  - Controls that sign out or leave the app are skipped.
- Records the observable effect: navigation, API call, dialog, download, file chooser, new tab or DOM change.

Each control is then classified as one of:
- `WORKING`
- `DISABLED`
- `NO_EFFECT`
- `BROKEN` (5xx or network error)
- `WRONG_PERMISSION` (403)
- `UNREACHABLE`

The run fails on any `NO_EFFECT`, `BROKEN` or `WRONG_PERMISSION` result, or on any screen load error. The results are in `test-results/action-audit.json`; the summary is in `UX-AUDIT.md`.

## 10. Performance

- **Route-level code splitting:** the guest and the admin are separate chunks, and so are QR, the Arabic dictionary, xlsx and zod.
- **Initial JS (gzip):**
  - The guest site loads react (59 KB) + app shell (64 KB) + shared domain code (21 KB) + guest chunk (41 KB).
  - It no longer downloads the admin entity registry (−3.6 KB); the category lists it needed moved to `shared/categories.ts`.
  - English admin sessions no longer download the Arabic dictionary: −37 KB gzip, and the admin chunk went from 124 KB to 92 KB, now including the entity registry that only the admin uses.
- **Images:** the media pipeline stores width variants. Cards request the variant that fits, lazy-load below the fold and reserve their aspect ratio (no layout shift).
- **Data:** the guest bundle is a single cached published snapshot (`staleTime` 60 s). Admin queries poll only where the data is live (requests, bell).

## 11. Known limitations

- Photos from external CDNs cannot be reached from the test sandbox, so screenshots show the branded fallbacks. Real hotel photos are uploaded through the media library.
- There is no payment gateway and no PMS integration (out of scope by decision).
- Settlement PDFs use the browser's print dialog.
- Engagement analytics are counts, not funnels per guest. This is deliberate for privacy.
